# Progression Refactor Design

**Date:** 2026-05-22
**Status:** Approved

## Problem

`app.js` contains a 24-entry `PLAN` array where every week's sets and reps are hardcoded. The
underlying periodization logic (macro volume jumps, micro weekly increments, rest week scaling) is
invisible — you have to diff rows by hand to see the pattern. Adding or tweaking a block means
editing up to 24 entries and hoping nothing drifts.

## Goal

Replace the `PLAN` array with a compact config + generator. The config should make the
periodization intent explicit and readable. The generator should be a handful of pure functions
that are independently testable.

Accepted constraint: a small number of rep values shift by ±1–2 vs the current hardcoded plan
(detailed below). All shifts are within noise for a home workout program.

---

## Program Structure

The 24-week program is built from two layers:

- **Blocks 1–5** (weeks 1–20): each block = 3 progressive weeks + 1 rest week. Generated by formula.
- **Block 6** (weeks 21–24): deload, test, maintain ×2. Stays as explicit config — no formula needed.

```
const PROGRAM = {
  numBlocks: 5,           // five formula-generated blocks (blocks 1-5) make up weeks 1-20
                          // block 6 (weeks 21-24) is explicit config, not generated
  activeWeeksPerBlock: 3, // weeks 1-3 of each block are progressive training
                          // week 4 is a rest/deload week (lower sets & reps)
  setJumpAtBlock: 3,      // MACRO PERIODIZATION: sets increase going into block 3.
                          //   blocks 1-2 → initialSets (lower volume phase)
                          //   blocks 3-5 → peakSets   (higher volume phase)
                          // When sets increase, startReps resets to absorb the new load.
  restFraction: 0.58,     // rest week reps = Math.round(blockPeakReps * restFraction)
                          // ~58% of peak keeps the rest week genuinely easy while
                          // maintaining movement pattern.
};
```

## Exercise Config

Two kinds of exercises:

### Formula exercises — push-ups and pull-ups

Their inter-block rep transitions follow a single rule, so `startReps` can be fully derived.

```js
// increment: reps added per active week within any block.
//   This is the MICRO periodization unit — how much harder each week gets.
//
// transitionBonus: extra reps added when starting a new block at the SAME set level.
//   Push-ups = 1: after a rest week you pick up one rep ahead of where you left off
//              (the rest paid off — you're slightly stronger).
//   Pull-ups = 0: after rest you re-enter at exactly the same rep count you peaked at
//              (pull-ups are harder to recover from; prudent to hold the rep count).
//
// initialSets / peakSets: the set count for the two volume phases (pre/post setJumpAtBlock).
// restSets: sets used on the rest week (always lower than active sets).

pushUps: { initialReps: 10, increment: 1, transitionBonus: 1,
           initialSets: 6,  peakSets: 7,  restSets: 4 },

pullUps: { initialReps: 5,  increment: 1, transitionBonus: 0,
           initialSets: 6,  peakSets: 7,  restSets: 4 },
```

**startReps derivation for formula exercises:**

```
startReps(b=0) = ex.initialReps

startReps(b) =
  setsOf(b) > setsOf(b-1)
    ? startReps(b-1)                    // MACRO RESET: sets increased → reps drop back to
                                        // where the previous block *started* (not peaked).
                                        // This compensates for the higher volume load.
    : prevEndReps + ex.transitionBonus  // MICRO CONTINUATION: same set level → carry reps
                                        // forward from the previous block's peak, plus the
                                        // transitionBonus if any.
```

### Config exercises — squats and crunches

Their inter-block transitions are non-uniform (squats: different bonus in phase 1 vs phase 2;
crunches: deliberate progressive taper of the final-week increment: 3→2→1→1→0). No single
`transitionBonus` covers them, so `blockStartReps` is stored explicitly as 5 values.

```js
// blockStartReps: the starting rep count for each of the 5 blocks.
//   Squats: [15, 22, 22, 26, 30]
//     - block 1→2: +2 bonus on transition (early phase, lower volume → aggressive rep jump)
//     - block 2→3: MACRO RESET back to 22 (sets 6→7)
//     - block 3→4 and 4→5: +0 bonus (high-volume phase, continue from peak)
//   Crunches: [15, 20, 22, 25, 28]
//     - no set jump (sets always = 3); progression slows each block intentionally
//       because crunches are an accessory lift — you don't chase infinite reps.

squats:  { blockStartReps: [15, 22, 22, 26, 30], increment: 2,
           initialSets: 6, peakSets: 7, restSets: 4 },

crunches:{ blockStartReps: [15, 20, 22, 25, 28], increment: 2,
           sets: 3,  // constant — no set jump for crunches
           restSets: 2 },
```

---

## Universal Within-Block Formula

Once `startReps(b)` is known (derived or explicit), all exercises use the same formula:

```
weekReps(b, w)  = startReps(b) + w * ex.increment
                  // w = 0 (week 1), 1 (week 2), 2 (week 3)
                  // Linear ramp within the block — each week is harder than the last.

endReps(b)      = weekReps(b, 2)   // peak of the block

restReps(b)     = Math.round(endReps(b) * PROGRAM.restFraction)
                  // Scales the rest week proportionally to whatever the block peaked at,
                  // so rest weeks stay appropriately easy even as the program advances.
```

## Value Shifts vs Current Hardcoded Plan

Active weeks only (rest week shifts are ±1–3 reps, acceptable):

| Exercise  | Shifted week(s)          | Old → New  | Reason |
|-----------|--------------------------|------------|--------|
| Push-ups  | Week 19 (block 5, w3)    | 20 → 21    | Uniform +1 increment; old plan manually capped at 20 |
| Pull-ups  | None                     | —          | Formula is exact |
| Squats    | Week 3 (block 1, w3)     | 20 → 19    | Old plan used +3 final-week bonus; formula uses uniform +2 |
| Crunches  | Last week of each block  | +0 to +2   | Old plan tapered final-week bonus (3→2→1→1→0); formula uses uniform +2 |

## File Structure

```
progression.js      — new: PROGRAM, EXERCISES constants + pure formula functions
                           (computeStartReps, weekReps, restReps, generatePlan)
                           loaded as a <script> tag before app.js
app.js              — modified: PLAN array removed, replaced by generatePlan() call
progression.test.js — new: Node.js assert-based tests (no framework needed)
index.html          — modified: add <script src="progression.js"> before app.js
```

Run tests: `node progression.test.js` — no npm, no framework, no setup.

---

## Test Strategy

Tests are written against the **formula's expected output** (not the old hardcoded values).
They serve as the contract for correctness: if the formula functions pass, the refactoring
preserved the progression logic.

Test coverage:
1. `computeStartReps(ex, blockIdx)` — all 5 blocks × 4 exercises
2. `weekReps(ex, blockIdx, weekInBlock)` — spot checks across all exercises
3. `restReps(ex, blockIdx)` — all 5 blocks × 4 exercises
4. `generateWeek(weekN)` — integration: checks sets & reps for a selection of weeks
   including the set-jump boundary (week 9), rest weeks, and the peak (week 19)
